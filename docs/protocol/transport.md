# 传输与事务

## HID 接口

当前 A80 配置接口的 VID/PID 为 `05AC:024F`，vendor usage page 为 `FF1C`，输入与输出 Report ID 都是 `04`。每个报告数据区为 63 字节，加上 Report ID 后线上共 64 字节。

官方有线抓包中为接口 1、interrupt OUT `03`、interrupt IN `82`。USB 地址随重新连接变化，WebHID 通过集合的 usage page、Report ID 和报告长度选择接口，不使用抓包中的临时总线地址。

```js
await device.sendReport(4, data63)
// inputreport: event.reportId === 4，event.data 为 63 字节
```

Report ID 不再放入 `data63`。正常配置流量不是早期探针使用的 17 字节控制传输形式。

## 帧格式

| data 下标 | 长度 | 字段 |
| --- | --- | --- |
| 0–1 | 2 | 请求求和校验，小端；部分应答替换为请求 CRC，大端 |
| 2 | 1 | 命令 |
| 3 | 1 | 有效载荷长度，0–56 |
| 4–5 | 2 | 字节偏移，小端 |
| 6 | 1 | 当前使用 `00`，语义未确认 |
| 7–62 | 56 | 载荷及尾部填充 |

请求校验：`sum(data[2..62]) & 0xFFFF`，低字节在前。长度字段之外的填充也参与求和，读请求的载荷通常为零。

读应答 `03/05/07/08/1B` 的头两个字节是 **CRC-16/MODBUS(request[2..62])**，高字节在前；初始值 `FFFF`，反射多项式 `A001`。该 CRC 关联的是原请求，不校验响应改写后的载荷。

例如设备信息请求以 `04 25 00 03 22 00 00 00` 开头（含 Report ID），读应答以 `04 39 B7 03 22 00 00 00` 开头；`39B7` 是原请求的 CRC。应答中的设备信息不能拿来重新计算这个值。

应答接受规则：

- 长度必须为 63，Report ID 必须为 `04`，`data[2..6]` 与当前请求相同。
- 读命令要求前缀匹配上述请求 CRC。
- `F0` 除 `data[7]` 改为 `FF` 外，其余字节与请求相同。
- 当前实现中的其他写入/前导/结束命令要求完整回显。

没有事务编号。同一时刻只允许一个未完成请求；超时后连接进入故障状态，重新连接前不再发送或自动重试，以免迟到应答被误认为后续应答。默认应答超时 1200 ms，一般事务在应答后间隔 35 ms；键位写事务有单独时序，见下文。

## 已使用命令

| 命令 | 长度/偏移 | 当前用途 | 接受方式 |
| --- | --- | --- | --- |
| `F0` | 0 / 0，初始化三次 | 握手样式，具体语义未知 | 单字节变化 |
| `01` | 0 / 0 | 读写事务前导 | 完整回显 |
| `02` | 0 / 0 | 读写事务收尾 | 完整回显 |
| `03` | 34 / 0 | 设备信息 | 请求 CRC |
| `05` | 1 或 26 / 0 | 配置读取；26 字节含背光 | 请求 CRC |
| `05` | 1 / 44 (`2C`) | 键盘 Windows/Mac 模式 | 请求 CRC |
| `06` | 26 / 0 | 背光配置写入 | 完整回显 |
| `07` | 五片，共 273 | 固定参考键位表 | 请求 CRC |
| `08` | 五片，共 273 | 当前键位表 | 请求 CRC |
| `09` | 五片，共 273 | 当前键位表写入 | 完整回显 |
| `0B` | 五片，共 273 | 自定义 LED 数据写入 | 完整回显 |
| `1B` | 56 / 0，35 / 56 | 91 字节索引状数据，语义未完整确认 | 请求 CRC |

`01/02` 的位置来自成功事务，不把它们推断成通用的 RAM/Flash 事务保证。未识别的设备信息、索引字段及命令不作为编辑入口。

## 初始化读取

当前 `readSnapshot()` 按以下顺序执行：

```text
F0 × 3
01
03(34, 0)
07 五片
1B(56, 0), 1B(35, 56)
02
01, 08 五片, 02
05(1, 0), 05(26, 0)
05(1, 44)
```

`07` 和 `08` 必须分开理解：实机将 A 改成 B 后，A 实际输出 b，`07` 仍返回默认 A，`08` 才返回 B。因此备份和写后校验都使用 `08`。重新插拔后 B 的 `08` 读回及恢复 A 已有实机确认。

## 键位写事务

所有 273 字节块使用以下分片。分片边界可以切开三字节键位，必须按字节偏移拼接。

| 片 | 偏移 | 长度 |
| --- | --- | --- |
| 1 | 0 | 56 |
| 2 | 56 | 56 |
| 3 | 112 | 56 |
| 4 | 168 | 56 |
| 5 | 224 | 49 |

主应用完整流程：

1. `01 → 07 五片 → 02`，核对设备参考表与支持的布局一致。
2. `01 → 08 五片 → 02`，读取写前当前表。
3. 复读 `05(1,44)`，确认键盘模式与生成草稿时一致。先完成配置、目标编码及重复兼容修饰目标检查。
4. 保存原始 273 字节备份。备份存储失败则不开始 `09` 写入。
5. `03(34,0) → 03(34,0) → 01 → 09 五片 → 02`。
6. `01 → 08 五片 → 02`，把全部 273 字节与实际发送表逐字节比较。

步骤 5 中，除最后一片外，收到应答后不再人为等待 35 ms；最后一片应答后等待 15 ms 再发 `02`。这是保留官方成功抓包时序，不是已经证明固件具有某个分片超时阈值。

最后一片只有 49 字节有效载荷，但 data 剩余七字节保留整块的 `block[217..223]`，对应前一片末尾。这些尾部字节参与校验。`09` 与自定义 LED 的 `0B` 都保留该抓包行为。

槽位 88 的参考表示与线上写表示不同，具体转换见 [键位文档](keymap.md#槽位-88-与原始备份)。写后比较不忽略这个槽位。

任何应答丢失、写后不一致都会停止；不会盲目自动恢复或重发整表。导出写前备份、当前读取和日志后，在确认设备状态的前提下恢复。键位备份只包含键位表，不是完整固件或背光备份。

背光的 `06` 和 `0B` 顺序、读回限制见 [背光协议](lighting.md)。
